## К чему стремимся

Все бесплатные ассеты Unity и ассеты, раздаваемые по промокоду со скидкой 100 %,
сами попадают на аккаунт(ы) Unity — без участия человека. **Деньги не списываются
никогда**: оплата нажимается только при итоге ровно 0.

Один репозиторий — несколько версий одной программы:

| Версия | Для чего | Состояние |
|---|---|---|
| Настольная: `run.bat` (Windows), `run.sh` (Linux, Steam Deck) | Человек запускает меню и выбирает источники | Работает |
| Сервер: Docker + `deploy.sh` | Сам раз в период читает новые посты каналов, бот пишет в Telegram | **Работает на настоящем сервере с 19.09**: один аккаунт, только Telegram-каналы, прогон раз в сутки |
| Один `.exe` для компьютерного класса (10+ ПК, без установки .NET) | Школьный класс, каждому свой аккаунт | Позже |

## Что дальше — по порядку

Первые три пункта — это доделки по серверу, они короткие. Дальше — большая работа.

### 1. Обновить сервер до 1.22.1 и проверить чтение каналов (на сервере)

Что было 19.09 на 1.22.0. Прокси нашёлся и прошёл проверку, но страницы через него то
приходили за 3 с, то не приходили за 12 с. Канал `unity_assets_1` не открылся ни с одной
из трёх попыток, и чтение ушло на запасной путь — браузер через тот же прокси (51 с на
страницу). Работу это не сорвало: новых постов просто не было.

Причина — замерено с Deck через тот же прокси. Страница весит 24 КБ и приходит
мгновенно. Долго только **открывается соединение** через прокси: от 4 до 30 с и больше,
каждый раз по-разному. Старое чтение ждало 12 с и обрывало примерно половину попыток.
А проверка прокси, прошедшая за 50 мс до чтения, уже открыла живое соединение, но
программа его закрыла и открывала новое.

Что сделано в 1.22.1:

- проверка прокси и чтение идут через один клиент — чтение продолжает соединение,
  открытое проверкой (`TelegramClientFor`);
- если ответа нет 6 с, параллельно открывается второе соединение, потом третье, и
  страница берётся с того, что ответило первым; общий срок — 36 с
  (`GetWithSpareConnectionsAsync`). В логе это строка «Прокси долго открывает
  соединение — параллельно открываем ещё одно»;
- дата сборки в строке версии: в Docker раньше показывалась дата файла `dotnet`
  («собрано 2026-08-21»), теперь — дата самой программы.

Обновить и проверить:

```
cd ~/UnityAssetsDownloader && git pull && ./deploy.sh
docker compose logs -f
```

На вопрос «Собрать и проверить всё по шагам?» можно ответить «д» — шаг Telegram сразу
покажет новое чтение. Что должно быть в логе:

- `ВЕРСИЯ ПРОГРАММЫ: 1.22.1` и сегодняшняя дата сборки;
- `Telegram читаем без браузера, через прокси: socks5://…`, после неё страницы каналов,
  **без** строки `Простым запросом каналы не открылись`;
- строка «Прокси долго открывает соединение…» допустима — это не ошибка, если страница
  потом пришла.

Если запасной путь браузером всё же включился — прислать `logs/errors.log` и лог прогона.

Отдельно стоит дождаться прогона, в котором реально есть новые посты: с 19.09 каналы
не обновлялись, поэтому добавление ассетов и выкуп по промокоду на новой версии
вживую ещё не проходили.

Прогон раз в 6 часов уже включён (19.09, временно — потом обратно на сутки:
`WATCH_INTERVAL=1d` в `.env`, затем `docker compose up -d`).

### 2. Мелкий долг по серверу (на сервере)

- **`SOURCES=all` вживую.** Поменять `SOURCES` в `.env`, затем `docker compose up -d`.
  Первый проход долгий (247 ссылок китайского архива плюс страницы магазина), дальше
  уже добавленные ассеты пропускаются по памяти профиля.

Права на файлы решено оставить как есть: контейнер работает от root, `./data` и `./logs`
принадлежат root. Сервер под одну задачу, администратор на нём тоже root, а запуск от
обычного пользователя пришлось бы оплачивать возней с правами на папку браузера — как
раз тем местом, которое уже ломалось (`SingletonLock`). Если когда-нибудь понадобится:
`user:` в `docker-compose.yml`, `chown -R` на `data` и `logs`, и отдельно убедиться, что
Chrome в контейнере запускается.

### 3. Проверка сессии Unity (на Deck, потом на сервере)

19.09 на сервере состояние сессии загрузилось, но быстрая проверка его не подтвердила,
и программа вошла заново — вход прошёл сам, код Unity не запросил. Похожее место:
проверка сессии иногда занимает 20 с вместо 8. В прогоне 19.09 06:53 (1.22.0) сессия
подтвердилась, но проверка заняла 31 с (06:53:27 → 06:53:58), а восстановление
cookies перед ней — ещё 8 с. Разобраться, почему быстрая проверка
не срабатывает: из-за этого каждый прогон рискует потребовать полный вход, а это
лишние минуты и лишний шанс, что Unity спросит код. С прогоном раз в 6 часов таких
входов будет до четырёх в сутки, так что цена вопроса выросла.

### 4. Несколько аккаунтов на сервере (отложено)

Решено 19.09: пока на сервере хватит одного аккаунта. Ниже — что делать, когда
понадобятся несколько. Сейчас одна служба = один профиль.
Предложение (обсудить): **одна служба, прогон по очереди для каждого аккаунта** —
один Chrome за раз, меньше памяти, одно расписание. `deploy.sh` спрашивает список
аккаунтов; учётки — в `.env` (`UNITY_ACCOUNTS=a,b`, `UNITY_EMAIL_a`, `UNITY_PASSWORD_a`…)
или по файлу на аккаунт. Каналы читаются один раз на прогон и раздаются всем
профилям; память (`owned_assets.txt`, `telegram_state.json`) — у каждого своя.
Альтернатива — по службе на аккаунт в `docker-compose.yml`: проще в коде, но
N браузеров и N прокси-подборов.

### 5. Один .exe для компьютерного класса (позже)

Та же программа, другая сборка: `dotnet publish -r win-x64 --self-contained
-p:PublishSingleFile=true`. Решить: меню `run.bat` встроить в exe или положить рядом;
браузер — системный Chrome или скачивание при первом запуске (сейчас PuppeteerSharp
качает его в папку программы). Копируется в сетевую папку, у каждого ученика свой
профиль (профиль по умолчанию = имя пользователя Windows — уже так).

### 6. Мелкое

- `run.bat`/`run.sh` не спрашивают про «только новые посты» — на ПК это и не нужно,
  но можно добавить пункт меню.
- Бесплатные прокси живут минуты: 19.09 запомненный прокси умирал между запусками
  трижды подряд. Сейчас это лечится перебором и списком найденных за прогон. Если

## Что важно знать, прежде чем что-то менять

Это выяснено опытным путём. Легко сломать обратно.

### Вход в Unity

- Адрес входа — `https://assetstore.unity.com/auth/login?redirect_to=%2F`. Прямые
  `login.unity.com/…/sign-in` уводят на регистрацию. Без `redirect_to` вход крутится по кругу.
- Форма двухшаговая: `input#email` → первая `button[type=submit]` «Continue»
  (ниже кнопки Google/Apple/Facebook/SSO — `type=button`) → пароль на следующем шаге.
  Поля заполняются нативным сеттером value, иначе React стирает.
- Первый клик сразу после открытия страницы теряется — ждём `readyState=complete`
  и ещё 1,5 с (`TryAutoLoginStepAsync`).
- **Каждый шаг отправляется один раз.** Раньше форма заполнялась на каждом проходе
  цикла, и неверный пароль слался минутами. Ошибка страницы, капча, второй отказ —
  остановка (`_autoLoginGaveUp`, причина в `_loginProblem`, сообщение боту).
- Вход через Google в браузере под управлением программы не работает и не будет —
  нужен пароль Unity ID.

### Профили

После первого входа профиль переименовывается: `server` → `server__betmansmall`.
`ProfileStore.FindRenamed`: если папки с заданным именем нет, а `имя__*` ровно одна —
берётся она. Без этого `--profile server` на сервере каждый прогон начинал бы с нуля.

### Корзина и оформление заказа по промокоду

- Корзина — `https://assetstore.unity.com/account/cart` (`/cart` — 404).
- Порядок: «Add to Cart» → корзина → убрать всё, кроме этого ассета (по одному: пока
  идёт удаление, остальные кнопки заблокированы; «Saved for Later» не трогать) →
  «Checkout» (`data-test="checkout-button"`) → вход через `api.unity.com/v1/oauth2/authorize`
  → `pay.unity.com/asv2/checkout?orderId=<id>`. Страницу оплаты узнавать по `Uri.Host`,
  а не по подстроке: `pay.unity.com` стоит в параметрах ссылки входа.
- **«Buy Now» на странице ассета не нажимать никогда.** Это Express Purchase: при
  привязанной карте списывает деньги сразу, без шага с промокодом (выяснено по JS магазина).

### Кнопки чужих ассетов на странице

На странице ассета есть блоки «ещё от автора», «похожие», «top free assets». У каждой
карточки своя кнопка «Add to Cart» и свой `data-test="add-to-cart-button"`. Поиск по
всей странице берёт первую подходящую — и она вполне может быть чужой: 19.09 на сервере
так в корзину попал `#267305` вместо `#321010`.

Поэтому кнопка проверяется на принадлежность: от неё поднимаемся вверх, пока не
встретится блок со ссылками на ассеты. Одна ссылка — это карточка одного ассета, и её
номер должен совпасть с нужным. Несколько ссылок — общий блок страницы, кнопка своя.
Так же проверяется «Add to My Assets» (там нужный номер берётся из адреса страницы).

Если своей кнопки нет, а чужие есть — ничего не нажимаем, ассет пропускается с
понятной причиной. Сценарии стенда: `P` (только чужие кнопки) и `Q` (своя кнопка среди
чужих).

### Чтение каналов Telegram

- Страница `t.me/s/<канал>` собирается на сервере Telegram: весь текст постов лежит в
  HTML, выполнять на ней нечего. Поэтому её качает обычный запрос, а не браузер.
- Листать страницу вниз бесполезно: отдаётся около 20 последних постов, более старые
  живут на `?before=<номер самого старого прочитанного>`.
- Ссылку в посте часто прячут за словом («Ссылка: тут»), поэтому к тексту поста
  дописываются адреса всех его ссылок. Без этого ассеты теряются.
- Пустая страница и заглушка провайдера — разные вещи. Настоящую страницу узнаём по
  разметке `tgme_`; если её нет, это ошибка сети с меткой
  `TelegramSourceParser.NetworkFailureMarker`, и программа берёт следующий прокси.
- Через бесплатный прокси долго открывается соединение (4–30 с), а не идёт страница.
  Поэтому проверка прокси и чтение делят один клиент и его соединения, а медленное
  открытие перекрывается запасными соединениями. Не возвращать отдельный клиент для
  чтения с коротким таймаутом — ровно это сломалось 19.09 на сервере.
- Браузерный разбор остался запасным и включается сам. Скриншоты постов без ссылок
  бывают только в нём — при чтении без браузера тексты и так лежат в
  `telegram_posts_raw.log`.
- Проверять правки удобно на настоящих страницах: они сохранены в `harness/fixtures/`,
  сценарий стенда `TH` сверяет быстрый разбор с браузерным. Обновить их:
  `curl -s https://t.me/s/unity_assets_1 -o harness/fixtures/unity_assets_1.html`

### Связь с Telegram Bot API

Путь до `api.telegram.org` подбирается перебором, первый ответивший запоминается в
`data/telegram_bot_route.txt`: путь из прошлого раза → напрямую → каждый из
закреплённых адресов Telegram → прокси, найденный для каналов. Соединение ждём 8
секунд: мёртвый путь должен уступить место следующему, а не съесть таймаут запроса.

Важные тонкости:

- DNS нередко отдаёт адрес, до которого у машины нет маршрута, хотя другие адреса того
  же сервиса отвечают. Проверено с Deck: из пяти адресов отвечает только
  `149.154.167.220`.
- При закреплённом адресе подменяется **только адрес назначения**. Имя в проверке
  сертификата и в заголовке `Host` остаётся `api.telegram.org`, иначе сломается TLS.
- Свой `ConnectCallback` отменяет `ConnectTimeout`, поэтому время соединения
  ограничивается вручную.
- Ответ Telegram с отказом (неверный токен, нет чата) перебор прекращает: путь тут не
  при чём. Перебор идёт только по сетевым ошибкам, поэтому сообщение не удвоится.
- **MTProto-прокси для Bot API бесполезен** — это другой протокол. Годятся только
  SOCKS5/HTTP-прокси и туннели.

Весь этот опыт добыт в соседнем проекте, там же диагностика и грабли:
`/home/deck/Code/AvtorProjects/server/LinuxServerWatcher/docs/telegram-access.md`.

### Страница оплаты pay.unity.com (скриншоты 18.09)

Язык и валюта зависят от аккаунта и страны: видели русскую с долларами, английскую с евро.
Сверху вниз:

1. Две галки: EULA **и** отказ от 14 дней одним текстом (внутри подписи ссылка на
   EULA — кликать саму галку); письма Asset Store. Потом «Pay now».
2. Сводка «Items (1) 18.40€ · Subtotal · Tax · **To pay now** 22.45€» (по-русски
   «Покупки … К оплате»).
3. «Enter Coupon/Credit Code to update your price», поле без говорящих атрибутов,
   «Apply». Поле ищется по подписи рядом. По CSS бывает и блок `.summary-coupon`
   (ошибка `dd.note .error`, отвергнутый код `.coupon-item span.invalid`).
4. **Tax Business use**: по умолчанию «Yes» и требуется «Tax number». Отвечать всегда
   «No» и проверять, что выбор сохранился: перед кодом, перед Apply и перед оплатой.
   Пока «Yes» — налог и итог прочерком, а код получает «Organization address info is
   not complete or correct» — это **не** отказ по коду: «No» и код ещё раз.
5. Payment method: по умолчанию PayPal с «Paypal email». При итоге 0 не мешает
   (PathGrid куплен так).

### Проверка цены — про деньги

- Оплата — только если итог ровно 0, у поля кода нет ошибки, обязательная галка стоит
  и в налоге «No» (`payBlocker` перед шагом 8).
- Сумма берётся **после слова итога** («to pay now», «order total», «к оплате»…),
  слово ищется целиком: «total» есть внутри «Subtotal» — при итоге прочерком раньше
  читался Subtotal. Валюта до или после числа: `$`, `€`, `£`, `₽`, коды.
- Никогда не возвращать поиск подстроки `0.00` — её содержит и `$10.00`.
- Ноль засчитывается, только если рядом нет ошибки: без посчитанного налога страница
  может показать что угодно.

### Какие отказы запоминаются

В `rejected_promocodes.txt` — только явный отказ по коду (expired, invalid…) или
частичная скидка. Непонятная ошибка или код без ответа — не запоминаются. 18.09 четыре
кода ошибочно попали туда из-за ошибки про адрес — файл был очищен.

### После «Pay now»

Магазин уводит на `assetstore.unity.com/orders/<id>/confirm`, страница меняется прямо во
время проверки. `VerifyPromoPurchaseAsync` ждёт до 30 с «Thank You For Your Purchase»,
а покупку подтверждает по «Open in Unity» на странице ассета. После нажатия оплаты
корзина не чистится.

### Telegram

- `t.me/s/<канал>` — около 20 последних постов; старые — `?before=<номер>`.
- Пачки (`--tg-batch-size`, по умолчанию 30): каналы по кругу, по странице с каждого,
  пока не наберётся N ассетов, которых нет в памяти профиля. `TelegramChannelCursor`
  помнит, где остановился каждый канал.
- «Только новые» (`--tg-only-new`, всегда в `--watch`): `telegram_state.json` хранит
  номер последнего поста; курсор получает `StopAtId`. Канал впервые — последние
  `postLimit` (50). Отметка сдвигается, только если каналы дочитаны, прогон не
  остановлен лимитом и это не `--dry-run`.
- Промокод: слово «промокод» в любой форме или promo code/coupon, затем код
  **латиницей** — заглавными или с цифрами («чтобы» кодом больше не считается).
- Каналы для сервера — в `TELEGRAM_CHANNELS` (`.env`), а не в `telegram_sources.txt`:
  тот в git, правка ломала бы `git pull`.

### Сервер и Docker

- `--watch`: прогон → пауза `--watch-interval` (от начала прогона) → прогон. Каждый
  прогон — новый `UnityAssetAutomationApp` и заново прочитанные параметры. SIGTERM между
  прогонами — выход с кодом 0; посреди — сохранить память и выйти сразу.
- Нет ни X11, ни Wayland (Docker, SSH) → браузер невидимый сам, в любом режиме.
- Chrome пишет блокировку `SingletonLock` с именем «компьютера»; у нового контейнера
  имя другое, и чужую блокировку Chrome не снимает — `RemoveStaleChromeLock` снимает её,
  а в `docker-compose.yml` постоянный `hostname`. Личный Chrome (пункт B) не трогается.
- `init: true` в compose — убирает зомби-процессы браузера.
- `.env`: значения в двойных кавычках с экранированием `\ " $` — так Compose v5
  передаёт любой пароль буквально (проверено `docker compose config`).
- Проверки выходят с кодом 2 при неудаче (`--check-login-page`, `--check-telegram`,
  `--notify-test`, `--login`) — по нему `deploy.sh` понимает, что шаг не прошёл.

### Разное

- JavaScript внутри C# компилятор не проверяет — после правки JS прогонять стенд.
- Логи должны оставаться читаемыми: тексты постов — в `telegram_posts_raw.log`,
  ошибки скриптов самого магазина (PAGE ERROR) — только в `--verbose`.
- `run.bat` — с переносами CRLF (иначе `goto` ломается), следит `.gitattributes`.
- На Deck `/tmp` чистится при перезагрузке: ничего ценного там не держать.

## Как проверять изменения

### Стенд (только на Steam Deck)

```bash
dotnet run --project harness              # все сценарии, ~10 минут
dotnet run --project harness -- G,L,N     # только нужные
```

Ни в магазин, ни в Telegram не ходит. Сценарии: `A–D, F` — выкуп (корзина, чужие
ассеты, истёкший код, частичная скидка), `G, H, L, M, I, J, K` — страница оплаты как
на скриншотах 18.09 (налог, галки, ошибка адреса, подтверждение, непонятная ошибка,
«No» не ставится), `E, N, O` — вход (успех, неверный пароль, код), `IV` — период,
`P` — промокоды, `T, TB, TN` — Telegram (разом, пачки, только новые), `id` — номер ассета.
Стенд вызывает внутренние методы через reflection: переименовали метод или поле —
поправьте имя в `harness/Program.cs`.

### Быстрые проверки, не трогающие аккаунт

```
--check-login-page     страница входа Unity: на месте ли поля
--check-telegram       каналы: сколько постов, ссылок, промокодов
--notify-test          бот: проверочное сообщение
--list-profiles        какие профили есть
--dry-run              полный проход без изменений аккаунта
```

В меню `run.bat`/`run.sh` это пункты **C**, **T**, **P** и **7**.

### Docker на Steam Deck

Docker нет, есть podman на хосте и Compose v5 в `~/.docker/cli-plugins/docker-compose`:

```bash
flatpak-spawn --host sh -c "cd $PWD && podman build -t unity-assets-downloader ."
flatpak-spawn --host podman run --rm --init -v ~/.cache/t/data:/app/data \
    -v ~/.cache/t/logs:/app/logs unity-assets-downloader --check-login-page
```

Папки для контейнера — в домашнем каталоге: `/tmp` песочницы Flatpak хост не видит.
Для `deploy.sh` целиком нужен сокет podman (`podman system service`) и обёртка
`docker`, которая ведёт `docker compose` в него.
